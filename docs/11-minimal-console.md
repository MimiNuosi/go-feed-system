# 阶段 11：最小前端控制台（人工验证）

## 目标与取舍

目标是让"项目到底能不能正常运行"变成**能点、能看**的事，而不是只靠 curl
和单元测试。之前每次验证都要手写一堆请求，而且没法直观看到 Feed 与热榜的样子。

参考项目（`LeoninCS/feedsystem_video_go`）有一个完整前端：Vue 3 + Vite + TS +
Pinia + vue-router，nginx 部署，11 个页面（首页、Feed、热榜、视频详情、私信、
个人主页、设置……）。但它的接口面比我们大：**token 刷新、分片上传、封面/头像
上传、私信、按作者列视频**这些我们都没有。照抄页面会做出一堆点不动的界面 ——
前端的形态是被后端能力决定的。

所以第一版做成：**单文件静态页（原生 HTML + fetch），由 API 同源提供**。

## 交付

```text
internal/web/index.html     页面本体：登录/注册、上传、关注 Feed、热榜、
                            我的视频、详情（播放/点赞/评论/关注/记录浏览）
internal/web/web.go         go:embed 把页面打进二进制
internal/router/router.go   GET / 返回该页面
internal/video/*            GET /api/v1/users/:id/videos（按作者列作品）
```

三个决定及理由：

```text
go:embed 而不是读磁盘
  镜像里只有一个二进制、不用挂载目录，Dockerfile 也不用改
  （构建阶段本来就 COPY 了整个仓库）。代价是改页面要重新编译，
  对"验证工具"来说可以接受。
同源提供而不是单独的 nginx
  不需要配 CORS、不需要代理、不需要多一个容器；
  生产环境应该交给 nginx/CDN，这里是为了开箱即用。
原生 fetch 而不是 Vue
  验证工具不需要构建链、路由和状态管理；需要的是"打开就能点"。
  代价是它讲不了前端工程化，所以不能当成"全栈"的论据。
```

## 覆盖的人工验证流程（六条）

```text
1. 注册 / 登录（401 时自动清登录态并提示）
2. 上传视频（multipart，走内容嗅探那条路）
3. 关注 Feed（复合游标 + "加载更多"）
4. 热榜（1h / 24h 切换 + 游标翻页）
5. 我的视频（按作者列作品 + 游标翻页）—— 发布过的东西永远找得回来
6. 详情页：<video> 播放（会触发 Range 请求）、点赞/取消、评论增删、关注作者
7. 记录一次浏览 —— 热榜里立刻能看到这个视频，形成可见闭环
```

## 为什么补了"按作者列视频"

第一版控制台上线后立刻暴露了一个体验断裂：**上传成功后，只有详情页那一次能看到
自己的视频**；一旦离开页面、或者退出重新登录，就再也找不回来了。而且换个账号
登录也看不到（那是对的：关注 Feed 只显示"我关注的作者"，热榜又需要热度，
新视频 0 分不进榜）。

根因不是页面，而是**后端缺一条接口**：没有"按作者列作品"，前端就做不出
"我的作品"页。参考项目有 `/video/listByAuthorID`，我们当时没有。

所以补了 `GET /api/v1/users/:id/videos?page_size=&cursor=`：

```text
公开可读（别人的作品列表也要能看），可选鉴权：
  登录后额外返回 is_liked_by，匿名时恒为 false
只返回 status=ready 的视频，按 id 倒序（最新发布在前）
作者不存在返回 404，而不是空列表 —— 否则调用方分不清
  "这个人没有作品"和"这个人不存在"
```

**游标设计**：这里的游标就是上一页最后一条的 video ID。

```text
对比关注 Feed 的 (created_at, id) 复合游标：
  那条列表的排序键是 created_at，同一毫秒可能有多条，必须带上 id 才能唯一定位；
  这条列表的排序键就是主键本身，id 单调递增，一个数字就够。
什么时候该用复合游标？排序键不唯一的时候。
```

## 又补了"最新"频道（发现路径的最后一环）

"我的视频"解决的是"作者找回自己的作品"，但另一个问题还在：**别人怎么发现他的作品**。

```text
/feed/following  只有我关注的作者 —— 前提是我已经关注了对方
/feed/hot        只有有热度的内容 —— 新视频 0 分进不去
结论：一个新人刚发的视频，除了作者自己，谁都不可能看到
```

关注功能本身早就有（`POST /users/:id/follow`，控制台详情页上也有按钮），
但**你根本点不到那个按钮** —— 得先看到对方的视频才能关注，而发现路径是断的。
所以补了 `GET /api/v1/feed/latest`（不需要登录，匿名可看）：

```text
和 /feed/following 的查询只差一处：不 JOIN 关注表
排序与游标复用同一套 (created_at, id) 复合游标 —— 同一毫秒可能发布多条，
只用时间戳定位会漏或重
返回结构与其它 Feed 完全一致，所以控制台几个列表共用同一套渲染逻辑
```

浏览器里验过完整链路：切"最新"能看到别人的新视频 → 打开 → 点"关注作者" →
回"关注 Feed"里就出现了对方的作品。这正是"666 能不能看到 333 的视频"的完整路径。

**一个测试教训**：给 `/feed/latest` 写集成测试时，我一开始断言"结果正好 3 条"，
测试立刻挂了 —— 因为"最新"是**全站**的，它老老实实把库里已有的真实视频
（包括在控制台上传的那条）也列了出来。集成测试共享同一个数据库时，
**不能假设表里只有自己造的数据**；正确做法是只断言种子数据之间的相对顺序与存在性。

## 验证结果

API 层（按页面的调用顺序逐条跑通）：

```text
注册 -> 登录 -> /users/me -> 上传(id=69, ready) -> 详情 -> Range 206
-> 浏览 204 -> 点赞 204 -> 评论 -> 关注 204 -> 关注 Feed 有数据
-> 热榜 1h 出现该视频
```

浏览器层（真实点击，用无障碍树与截图核对）：

```text
注册成功 -> 登录成功 -> 热榜渲染出真实数据（"UI 验证视频 @ui3121752 播放 1 点赞 1"）
-> 打开详情（播放器渲染、点赞后按钮变"取消点赞"、点赞数 1→2、评论列表与发表框可用）
-> 关注 Feed 空状态正确
-> 切"我的视频"：空状态 -> 在页面上选择文件上传（提示"上传成功，视频 ID 75"）
-> 返回列表再切"我的视频"：列表里出现《控制台上传测试》并可直接打开
```

顺带用接口层复现了最初的困惑：用户 106（"333"）的作品列表能正常列出他的《老吴》
（`GET /api/v1/users/106/videos` -> 1 条），不存在的用户返回 404，非法游标返回 400。

## 播放量为什么"看完不涨"（三个原因叠在一起）

在控制台点开视频、看完、回列表，播放量没变。排查下来是三件事，每一件单独看都是对的：

```text
1. 播放本身不会发请求。播放量要显式 POST /api/v1/videos/:id/view 才会记，
   而控制台原来只有一个「记录一次浏览」按钮在调它。这是控制台的缺口，不是后端的问题。
2. 计数是异步落库的。/view 只把增量写进 Redis，MySQL 由回写 Worker 每 5 秒批量更新。
3. 同一个用户对同一个视频 5 分钟内只算一次（去重键 TTL 5 分钟），这是防刷量。
```

对应到代码：`/view` 在 Redis 里用一段 Lua 原子地做三件事 ——
`SET NX` 去重键、`HINCRBY` 待回写增量、`ZINCRBY` 热榜分数
（`internal/hot/redis_repository.go` 的 `recordViewScript`）；
`internal/hot/writeback.go` 的 `ViewWritebackWorker` 每 5 秒把这批增量
`UPDATE videos SET view_count = view_count + delta` 累加进 MySQL。

**修复的是第 1 条**：控制台给播放器加了 `timeupdate` 监听，播满 3 秒自动提交一次浏览，
并在 6 秒后重新拉一次详情把数字刷出来。第 2、3 条是设计，不是缺陷，所以提示语里
直接写清楚"约 6 秒后刷新、同一用户 5 分钟内只计一次"。

实测（视频 90，新注册用户 123）：

```text
before  view_count=0
POST /videos/90/view   -> 204
+7s     view_count=1      （等到了一个回写周期）
POST /videos/90/view   -> 204   （同一用户再点一次）
+7s     view_count=1      （被 5 分钟去重挡下）
```

浏览器层同样验证过：打开《控制台上传测试》（id=75，播放 0）→ 点播放 →
4.5 秒后出现提示"已记录浏览，约 6 秒后播放量刷新" → 再等 7 秒，详情变成"播放 1"。

**这套设计换来了什么**：一次播放 = 一次 Redis 写入，而不是一条
`UPDATE videos SET view_count = view_count + 1`。热点视频 1 万次播放就是 1 万次行锁竞争，
异步回写把它压成每 5 秒一条批量更新。

**代价**：进程死在"增量进了 Redis、还没回写 MySQL"之间，这部分播放量会丢；
写库成功但 `HDEL` 失败会多算一次。回写里的顺序因此是"先写库、后 ack"，
取舍是宁可多算、不可少算（和 outbox 的思路一致）。

## 顺手修掉的一个回归（值得记）

**现象**：上传接口返回 500 `INTERNAL`，而阶段 9 的端到端测试里它是好的。

**根因**：`outbox_events.payload` 是 JSON 列，而我在阶段 10 的压测优化里给
DSN 加了 `interpolateParams=true`。这个开关让 go-sql-driver 在客户端做参数转义，
**`[]byte` 参数会被写成 `_binary'...'`（binary 字符集）**，MySQL 拒绝用它构造
JSON 值：

```text
Error 3144 (22032): Cannot create a JSON value from a string with CHARACTER SET 'binary'
```

驱动源码可以确认这个分支（`connection.go`）：`[]byte` → `_binary'...'`，
`string` → 使用连接字符集。**修复**：把 `outbox.Event.Payload` 从 `[]byte`
改成 `string`（语义上它本来就是 JSON 文本），投递给 RabbitMQ 时再转回 `[]byte`。

为什么压测没发现：**压的全是读接口**，写路径根本没被覆盖。
为什么集成测试也没发现：集成测试的 DSN 来自 `TEST_MYSQL_DSN`，
而我手动拼的 DSN 没带 `interpolateParams=true`，**和生产不一致**。

两条教训：

```text
1. 压测要覆盖写路径，否则"性能没问题"和"功能没问题"是两件独立的事。
2. 集成测试的 DSN 必须和生产同款参数，否则驱动层面的行为差异测不出来。
```

所以现在的验证命令是带参数的（这也是以后跑集成测试的推荐姿势）：

```powershell
$env:TEST_MYSQL_DSN='feed_app:<pass>@tcp(127.0.0.1:13308)/go_feed?charset=utf8mb4&parseTime=True&loc=Local&interpolateParams=true'
go test -count=1 ./internal/outbox/ ./internal/video/
```

## 已知局限

```text
1. 页面只覆盖我们已有的接口；没有搜索、私信、分片上传、头像/封面
2. 单文件内联脚本，没有 CSP；生产环境应交给 nginx/CDN 并用独立的前端工程
3. 上传是整文件 multipart（后端也只支持这个），大文件场景需要改分片
```
