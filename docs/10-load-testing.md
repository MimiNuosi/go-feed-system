# 阶段 10：压测与性能调优

前面九个阶段把功能做完了，但所有结论都只是"设计上正确"。
这个阶段的目标是把它们变成数字：

```text
系统在什么速率下开始变慢？
慢在哪一层（Go、MySQL、Redis）？
缓存和限流真的起作用了吗？
```

## 先搞清楚压测的几个概念

```text
QPS / RPS          每秒完成的请求数，就是吞吐量
P50 / P95 / P99    分位数。P95 表示 95% 的请求比这个值快。
                   平均延迟会把长尾藏起来：99 个 10ms + 1 个 5s，
                   平均只有 60ms，看起来很好，但那个用户等了 5 秒
Little's Law       并发数 = QPS × 平均延迟。
                   所以"能扛多少并发"必须带上延迟才有意义
```

**闭环 vs 开环**，这是决定压测结果可不可信的关键：

```text
闭环（固定并发数）  只有 N 个工人，一个请求返回了才发下一个。
                  系统变慢时压力自动变小 —— 问题被掩盖了。
                  这就是 coordinated omission（协调遗漏）：
                  真实用户不会因为服务变慢就不来，他们照样每秒点，
                  只是都堵在队列里。
开环（固定速率）    不管系统多慢，每秒都发固定数量的请求。
                  找拐点必须用开环。
```

vegeta 的 `-rate=N -duration=10s` 就是开环；`-rate=0` 是不限速打满。

## 环境与方法

```text
宿主          32 逻辑核 / 15.2 GB
Docker        api、mysql、redis 各限 6 CPU / 6 GB（同一台机器上）
工具          vegeta v12（go install github.com/tsenart/vegeta/v12@latest）
数据量        4 个视频、少量用户与互动，属于"数据量极小"的场景
```

必须写进结论的前提：**压测客户端和服务跑在同一台机器上**，
会互相抢 CPU。判断客户端是不是瓶颈的办法是看
`Requests` 行的 rate 与 throughput 是否一致 —— 一致说明客户端把
预定速率发出去了，瓶颈在服务端一侧。

三个被测接口刻意选了三种负载形态：

```text
GET /livez                      纯 Go HTTP 路径（探针，豁免限流）—— 天花板参考
GET /api/v1/feed/hot?window=1h  本地缓存 + singleflight，几乎全内存
GET /api/v1/videos/1            MySQL 查询 + 点赞聚合，无缓存
```

## 10.1 把限流额度做成可配置（已完成）

不做这一步，压到 1000 rps 以上返回的全是 429，测到的是限流器的天花板，
而不是系统本身的能力。

```text
RATE_LIMIT_ENABLED            默认 true，压测基线时设为 false
RATE_LIMIT_GLOBAL_BURST       默认 2000
RATE_LIMIT_GLOBAL_INTERVAL    默认 1ms
RATE_LIMIT_IDENTITY_BURST     默认 480
RATE_LIMIT_IDENTITY_INTERVAL  默认 250ms
```

`compose.yaml` 里用 `${VAR:-default}` 透传，所以压测时不用改文件：

```powershell
$env:RATE_LIMIT_ENABLED='false'; docker compose up -d api
```

验证：关闭后打 2500 次请求全部 200（若限流生效，2000 次之后应出现 429），
启动日志同时给出 `rate limiting is disabled by configuration`。

## 10.2 基线：三个接口的对比（500 rps × 10 秒，各 5000 次请求）

```text
接口               mean      P50       P95        P99        max      成功率
/livez             578µs     523µs     1.047ms    1.105ms    3.788ms  100%
/feed/hot          566µs     525µs     1.033ms    1.087ms    4.140ms  100%
/videos/1（DB）    2.295ms   2.085ms   2.657ms    3.232ms    55.035ms 100%
```

结论：**热榜接口和零成本的探针一样快**（566µs vs 578µs），说明
本地缓存 + singleflight 把这条路径变成了纯内存操作；
而走 MySQL 的详情接口慢 4 倍，瓶颈在数据层，不在业务逻辑或框架。

## 10.3 拐点：`GET /api/v1/videos/1` 的速率阶梯

```text
速率      mean      P50       P95        P99        max       成功率
500       2.295ms   2.085ms   2.657ms    3.232ms    55.035ms  100%
1000      2.049ms   2.091ms   2.657ms    3.231ms    7.852ms   100%
2000      2.238ms   2.100ms   3.161ms    5.126ms    33.173ms  100%
2500      2.340ms   2.125ms   3.660ms    5.263ms    19.088ms  100%
3000      2.793ms   2.612ms   4.855ms    7.681ms    20.507ms  100%
3500      3.881ms   3.144ms   8.219ms    19.188ms   66.777ms  100%
4000      6.272ms   4.223ms   17.891ms   42.675ms   106.827ms 100%
```

同一台机器上 `/livez` 的对照：

```text
/livez @ 2000 rps   mean 581µs  P95 1.070ms   P99 1.677ms
/livez @ 4000 rps   mean 540µs  P95 0.610ms   P99 1.055ms    <- 依然平坦
```

结论：

```text
1. 拐点在 2500 ~ 3000 rps 之间：2000 rps 时 P95 还是 3.2ms，
   3000 开始上翘，4000 时连 P50 都从 2.1ms 涨到 4.2ms。
   P50 一起涨，是队列开始堆积的信号（排队延迟打到了所有请求，
   而不是只有长尾）。
2. 全程 100% 成功，没有错误：系统是用延迟退化，不是用报错退化。
3. 同一时刻 /livez 压到 4000 rps 仍然平坦，说明瓶颈不在
   Go 框架、HTTP 栈或路由，而在数据库这条路径上。
```

## 10.4 瓶颈定位（在 4000 rps 稳态采样）

```text
容器 CPU       api 196%    mysql 200%    redis 2.4%     （每个容器上限 600%）
MySQL 连接     Threads_connected 21 / 池上限 20，Max_used_connections 22
MySQL 查询     Queries 在约 3 秒内从 1313957 涨到 1473182（约 4 万条/秒）
```

解读：

```text
1. redis 几乎不参与（2.4%），排除 Redis。
2. api 容器用掉约 2 个核，还没到 6 核上限 —— 服务端还有算力余量，
   说明延迟是"等数据库"，不是"自己算不过来"。
3. MySQL 用掉约 2 个核，连接池 20 条连接全部占满，
   每秒要执行 4 万条语句 —— 这是当前真正的瓶颈层。
4. 一个请求在详情路径上要发 3~4 条查询（视频、作者、点赞数、
   是否点赞），这也是放大倍数高的原因。
```

## 10.5 优化与复测（待做）

按"先测量再优化"的顺序，候选方案和预期：

```text
A. 减少每请求的查询数（推荐先做）
   详情路径的 3~4 条查询可以合并或去掉重复的，
   直接按比例降低 MySQL 的语句压力。
B. 给详情加短 TTL 读缓存
   收益大但会引入"点赞数短暂陈旧"的问题，需要先定可接受的陈旧窗口。
C. 调大 MySQL 连接池（MaxOpenConns 目前写死 20，也应该做成配置）
   注意：MySQL CPU 已经打满，盲目加大连接池只会让更多并发查询
   挤进数据库，延迟可能更差。这是一个"看着像优化其实可能变坏"的典型，
   必须复测后才有结论。
```

## 面试追问

1. 为什么压测要用开环而不是固定并发数？什么是协调遗漏？
2. 为什么看 P95/P99 而不是平均延迟？
3. 你的系统能扛多少 QPS？这个数字的前提是什么（机器配置、数据量、读写比例）？
4. 拐点是怎么判断出来的？为什么 P50 一起涨比 P99 涨更能说明问题？
5. 为什么不能简单地调大数据库连接池？
6. 缓存把热榜接口压到和探针一样快，代价是什么（数据陈旧、内存、冷启动）？
7. 压测客户端和服务在同一台机器上，会带来什么偏差？你怎么排除客户端是瓶颈？
